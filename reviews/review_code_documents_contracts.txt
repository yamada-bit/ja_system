No.1 【優先度: 高】 契約書の編集で「論理削除済みの関連書類」への紐付けが黙って消える  ★対応済み（2026-09-09）
  対応: contracts.services.filter_valid_related_ids に keep_ids 引数を追加し、既に紐付いている
  契約書pk（論理削除済みを含む）は入力リストに残っている限り維持する。ContractEditView.post /
  BulkEditView.stage_extra の両経路で keep_ids=obj.related_links... を渡す。正常操作時の
  「紐付け不可」警告ログも出なくなった。回帰テスト contracts.tests
  ContractEditViewFileHandlingTests に2件追加。
  対象ファイル:
    - contracts/services.py:142  filter_valid_related_ids （is_deleted=False で絞る箇所）
    - contracts/services.py:99   sync_related_contracts （全量同期＝リスト外を delete）
    - contracts/views.py:414-421 ContractEditView.post
    - contracts/views.py:581-588 BulkEditView.post（ステージ時にも同じ絞り込み）
    - templates/contracts/edit.html:129-135（削除済み行も hidden input を出力）
  根拠 / 想定シナリオ:
    契約書A が契約書B を関連書類として紐付けている状態で、B が論理削除される
    （検索詳細の削除 or 一括編集の削除。物理 purge の前、最大1ヶ月間）。
    その後 A をどの項目でも編集して「更新」すると:
      1. edit.html は related_rows の全行（削除済みB を含む）に hidden input
         related_contract_ids=B.pk を描画する。
      2. ContractEditView.post が filter_valid_related_ids() を通す。同関数は
         Contract.objects.filter(pk__in=..., is_deleted=False) で valid を作るため
         B.pk は valid に入らず「紐付け不可」として除外される
         （かつ logger.warning("紐付け不可の契約書pkが関連書類に指定された…") を出力
         ＝正常操作なのに不正アクセス試行のログが毎回残る）。
      3. apply_contract_edit() → sync_related_contracts(A, B抜きリスト) が
         ContractRelation A→B 行を delete。
    contracts/models.py:146-147 の ContractRelation docstring は
    「論理削除（is_deleted=True）の場合は行は残り、検索・閲覧画面で『既に削除されて
    いる関連資料です』と赤表示する」と明記しており、実装がこれに反する。B は削除済みの
    ため関連書類ポップアップ検索（RelatedSearchAPIView、is_deleted=False）から選び直す
    こともできず、紐付けは復旧不能。単独編集・一括編集の両経路で発生する。
  補足: documents 側に関連書類機能は無く、この指摘は contracts 単独。

No.2 【優先度: 中】 新規保管時の保存満了日が UTC 日付基準で、深夜帯に1日ずれる  ★対応済み（2026-09-09）
  対応: documents/contracts の UploadStep2View.post で save_date = timezone.now() を
  timezone.localdate() に変更し、calculate_expiry_date へ JST の localdate をそのまま渡す。
  編集時再計算・プレビューと同じ基準に統一。回帰テスト documents.tests
  UploadStep2PerFileMetadataTests.test_expiry_date_uses_jst_today_not_utc_date を追加。
  対象ファイル（documents/contracts で同一原因、1件に統合）:
    - documents/views.py:161,189  save_date = timezone.now() → calculate_expiry_date(save_date.date(), …)
    - contracts/views.py:231,260  save_date = timezone.now() → calculate_expiry_date(save_date.date())
  根拠:
    settings は USE_TZ=True / TIME_ZONE="Asia/Tokyo"（config/settings/base.py:108,110）。
    timezone.now() は UTC の aware datetime のため、.date() は UTC 日付を返す。
    例: 日本時間 2026-09-09 06:00 は UTC では 2026-09-08 21:00 で、.date() = 09-08。
    このため JST 00:00〜09:00 の登録では expiry_date が本来より1日手前で保存される。
    一方:
      - 編集時再計算 apply_document_edit():145 は timezone.localdate() を使用
      - プレビュー expiry_date_previews():184 も timezone.localdate() を使用
    ＝ 利用者が画面で見た満了日プレビューと実際に保存される値が深夜帯で食い違い、
       編集経路とも不整合。修正は save_date.date() を timezone.localdate() に統一。

No.3 【優先度: 低】 一括編集（契約書）で「関連書類の並べ替えのみ」の変更が黙って破棄される  ★対応済み（review_pending.txt 経由でリリース前に対応。U-19）。contracts/views.py commit_one_update の related_changed を set 比較から順序保持比較（list(staged_ids) != current_ids）へ変更し、単独編集経路（apply_contract_edit を無条件呼び）と揃えた。回帰テスト：contracts.tests.BulkEditViewTests に test_related_contracts_reorder_only_is_committed_on_update / test_related_contracts_same_order_is_not_dirty を追加。あわせて review_test_doc_contract [17]/[18]（U-37）・[19]（#65）相当も検証。accounts/contracts 304件 PASS。
  対象ファイル:
    - contracts/views.py:713  related_changed = staged_ids is not None and set(staged_ids) != set(current_ids)
    - contracts/services.py:160 contract_edit_is_dirty（related_changed をそのまま dirty 判定に使用）
  根拠:
    related_changed は set 比較のため、紐付け先の増減が無く順序だけ入れ替えた場合
    False になる。他項目も未変更なら contract_edit_is_dirty=False → status「更新なし」で
    apply_contract_edit() を呼ばず、display_order の変更が確定されない。
    単独編集（ContractEditView）は apply_contract_edit() が dirty 判定に関わらず必ず
    sync_related_contracts() を呼ぶため並べ替えが保存され、挙動が経路間で非一貫。
    ContractRelation.Meta.ordering=["display_order","id"] で順序は画面表示に反映される
    ＝利用者から見える変更。

No.4 【優先度: 中】 BulkEditView が documents/contracts でほぼ全文重複  ★対応済み（2026-09-09）

No.6 【優先度: 低】 契約書 BulkEditView._commit の prefetch_related が空振り  ★見送り／理由: 優先度「低」。指示により低優先度は修正せず記録のみ。No.4 の共通化で該当コードは core.bulk_edit_views.BaseBulkEditView.commit_queryset / contracts 側 commit_one_update へ移動したが、prefetch 空振りの構造（.values_list がキャッシュを使わない）は同じ。一括編集の対象は最大でも一覧選択ぶんで件数が限られるため実害小。
  対象ファイル:
    - contracts/views.py:626-629  Contract.objects.prefetch_related("related_links").filter(pk__in=pks)
    - contracts/views.py:709-711  obj.related_links.values_list("related_contract_id", flat=True)
  根拠:
    related マネージャに対する .values_list() は prefetch キャッシュを使わず都度 SELECT する。
    そのため prefetch_related("related_links") の結果は一度も参照されず、
    対象件数ぶんの追加クエリだけが発生する。prefetch を外すか、
    list(obj.related_links.all()) 経由で related_contract_id を取り出す。

No.7 【優先度: 低】 契約書 UploadStep2View.post が保存ループ内で権限クエリを毎回再発行  ★見送り／理由: 優先度「低」。指示により低優先度は修正せず記録のみ。一括登録のファイル数は実運用で数件程度、クエリも軽く実害は小さい。許可部署IDのループ前解決は filter_valid_related_ids のシグネチャ変更を伴うため別途。
  対象ファイル:
    - contracts/views.py:271-275  ループ内 filter_valid_related_ids(..., employee=request.user)
    - contracts/services.py:141   filter_valid_related_ids 内の contract_searchable_department_ids(employee)
  根拠:
    contract_searchable_department_ids() は内部で DepartmentViewScope と
    contract_visible_departments(M2M) の2クエリを発行する。ファイル N 件の一括登録で
    3N クエリになる。許可部署 ID をループ前に1回解決し、ファイルごとの pk 検証だけを
    ループ内で行う形に分離できる（contracts.forms.SearchForm が form.contract_dept_ids で
    同種の使い回しを既に実施済み）。

No.8 【優先度: 低】 RELATED_SEARCH_LIMIT がハードコード（.env 未経由）  ★見送り／理由: 優先度「低」。指示により低優先度は修正せず記録のみ。指摘本文どおり SearchView.PAGE_SIZE 等と同じ「容易に変更する運用値ではない内部定数」の前例があり、env 化するかはユーザー確認事項。確認が取れてからまとめて対応。
  → 2026-09-18ユーザー確認・現状維持で確定：xlsx 保管!B480の根拠は「簡易的に検索」とあるのみで、
    運用担当者が変更できる必要があるとの記載は無い。関連契約書検索ポップアップの描画コストに
    合わせた実装都合の値であり、SearchView.PAGE_SIZE=100・DELETE_WINDOW_DAYSと同じ「内部定数」
    として.env化しない方針で統一。コード変更なし。
  対象ファイル:
    - contracts/api.py:25  RELATED_SEARCH_LIMIT = 50
  根拠:
    CLAUDE.md「新しい設定値は django-environ 経由（env(...) 等）で .env から読み込める
    ようにし、.env.example にも追記する」。Rev1.6 で追加された返却件数上限だが
    モジュール定数のまま。
    ※ ただし SearchView.PAGE_SIZE=100 や core.deletion_services.DELETE_WINDOW_DAYS も
      同様にハードコード定数であり「容易に変更する運用値」ではない内部定数としての
      前例がある。env 化するか、内部定数として許容するかの判断はユーザー確認事項。

その他確認したが問題無しと判断した主な点:
  - bare except は無し。例外は (TypeError, ValueError) / (OSError, DBError) / DBError /
    InvalidOperation 等、具体型で捕捉し logger.exception 済み。
  - ページネーションは両 SearchView とも Django Paginator。関数ベースビュー無し。
  - scoped_get_object_or_404 による部署スコープ外 URL 直打ち対策、二重送信トークン、
    can_download / can_edit_contract のサーバー側再チェックは一通り実装済み。
  - 一括編集セッション state の pk 型（staged は str キー、pks/to_delete は int）は
    JSON 直列化と整合が取れている。
  - _add_years / _add_months / calculate_expiry_date の閏年・月末処理は正しい。
