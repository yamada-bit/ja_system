[低] 指摘4: api.py → views.py への import 方向
--------------------------------------------------------------------------------
対象:
  - documents/api.py:17  from documents.views import PENDING_SESSION_KEY
  - contracts/api.py:13  from contracts.views import PENDING_SESSION_KEY, RequiresContractEditMixin

内容:
  api.py が views.py の定数・ミックスインを取り込む形で、通常の依存方向（views → api ではなく
  api → views）とは逆になっている。循環importにはなっておらず（views.py は api.py を import
  しない、urls.py が両方を import）動作上の問題は無いが、セッションキー定数や
  RequiresContractEditMixin を中立な場所（例: 各アプリの services.py、または定数モジュール）に
  置く方が構成として素直。CLAUDE.md のファイル役割分担に「api はビュー内AJAX用」とあり、
  ビューへの逆依存を禁じてはいないため[低]。

[低] 指摘5: BulkEditView._commit のオーケストレーションが view 側に集中
--------------------------------------------------------------------------------
対象:
  - documents/views.py:472-546  BulkEditView._commit
  - contracts/views.py:552-646  BulkEditView._commit

内容:
  一括編集の確定処理は「ステージ済み全ページの検証ループ → transaction.atomic() 内で
  削除マーク適用 / dirty判定 / apply_*_edit / 監査ログ / status集計」という一連のビジネス
  ロジックを _commit メソッド（view 内）に持っている。フィールドコピーと dirty 判定自体は
  services.py（apply_document_edit / document_edit_is_dirty ほか）に分離済みだが、
  トランザクション制御と一括確定のフロー本体は view に残る。
  単体編集経路も transaction 制御を view 側に置いているため既存の慣習とは一貫しており、
  「規約違反」とまでは言えない。ただし _commit は分岐が多く、
  review_code_doc_contract_full.txt の C-6（確定パスの対象再取得にスコープ条件が無い等）とも
  重なる領域なので、services 側に bulk_commit(...) 相当を切り出すとテスト容易性・
  責務分離の両面で改善余地がある。

（参考・スコープ境界）
  templates/documents/edit.html の C-1 対応で追加された
  data-current-expiry="{{ document.expiry_date|date:'Y-n-j' }}"（ゼロ埋め無し）は、

  コードレビュー範疇の軽微な表示不整合のため参考記載に留める。
