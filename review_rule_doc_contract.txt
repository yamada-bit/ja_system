No.1  【中】 権限拒否イベントが audit（操作履歴ログ）に記録されない
--------------------------------------------------------------------------------
対象:
  - contracts/views.py:89-98  RequiresContractEditMixin.dispatch
  - contracts/views.py:742-757 DeleteView.extra_permission_check
  - contracts/api.py:62-68     DetailAPIView.get（他部署アクセス拒否）
  - contracts/api.py           RelatedSearchAPIView（Mixin経由）
  - contracts/services.py:124-169 filter_valid_related_ids（紐付け不可pyの除外）
  - documents/api.py:46-52     DetailAPIView.get（他部署アクセス拒否）
  - documents/search_services.py:78-83 / contracts/search_services.py:72-77
    （pks 改ざん検出）
  - documents/services.py / contracts/services.py の scoped_get_object_or_404
    （core.scoping_services 経由の warning のみ）

根拠:
  CLAUDE.md 規約「監査が必要なイベント（ログイン/ログアウト、権限に関わる操作等）は
  一元的な記録機構（audit アプリ）を通す」。
  上記はいずれも「契約書情報変更権限が無い職員の保存・削除操作」「他部署文書/契約書への
  URL 直打ちアクセス試行」「フォーム改ざんによる不正 pk 混入」という“権限に関わる操作”
  だが、記録は logger.warning のみで audit.AuditLog（＝操作履歴ログ画面・CSV出力の対象）
  には残らない。accounts/permissions 側では権限変更・ログイン等を audit_services.log で
  記録しており、拒否イベントだけ可観測性が一段低い。

補足（対応要否の判断材料）:
  - コードベース全体で「拒否試行は logger.warning、成功操作は AuditLog」という運用が
    一貫しており、documents/contracts 固有の逸脱ではない。
  - 操作履歴ログはエンドユーザー向け画面であり、拒否試行を意図的に除外している可能性も
    ある（その場合は本指摘は「規約文言の解釈の明文化」で足りる）。
  → 少なくとも「他部署リソースへの直打ちアクセス試行」はセキュリティ監査上価値が高いため、
    audit 記録の要否をユーザーに確認し、方針を CLAUDE.md か
    HTML_REIMPL_CHECKLIST_ARCHIVE 系に明記することを推奨。

対応済み（2026-09-09、ユーザー確定＝「他部署直打ちのみ記録」）:
  「他部署リソースへの URL 直打ちアクセス試行」だけを AuditLog（操作履歴ログ画面・CSV出力の
  対象）へ記録するようにした。権限不足の保存・削除操作やフォーム改ざんによる不正 pk 混入は
  従来どおり logger.warning 止まり（監査価値と操作履歴ログのノイズ増加のトレードオフ判断）。
  - 新設: audit.services.log_denied_cross_department_access（action="アクセス拒否"、
    event_message="部署スコープ外の{文書|契約書}（ID:n）へのアクセスを拒否しました。"）。
  - core.scoping_services.scoped_get_object_or_404 に任意コールバック on_denied を追加。
    documents.services / contracts.services のラッパーがこれを渡し、DownloadView /
    PreviewView / Edit / Delete / 一括編集の直打ちを一括カバー。masters（分類・カテゴリー）側は
    管理者用画面で監査価値が相対的に低いため on_denied を渡さず warning のみ据え置き。
  - documents/api.py・contracts/api.py の DetailAPIView.get は scoped_get_object_or_404 を
    経由しない直書き判定のため、同関数呼び出しを個別に追加。
  - テスト追加: documents/contracts の DepartmentScopeAccessControlTests に
    test_cross_department_direct_access_is_recorded_in_audit_log /
    test_own_department_access_does_not_write_audit_denial、DetailAPI テストにも AuditLog 検証。
  - 方針を CLAUDE.md「監査が必要なイベント」節に明記。

No.2  【低】 views.py に DB アクセスを伴う業務ロジックのヘルパー関数が残存
--------------------------------------------------------------------------------
対象:
  - contracts/views.py:792-808  _resolve_related_rows（Contract.objects.filter を実行）
  - contracts/views.py:780-789  _related_rows_for_contract
  - contracts/views.py:811-835  _merge_related_into_field_sets / _remap_related_ids_after_remove

根拠:
  CLAUDE.md「各アプリ内のファイル役割分担パターン」＝「services.py（ビューから分離した
  ビジネスロジック）」。関連書類 pk リスト → 表示行への解決や再描画時のインデックス
  詰め直しは、hidden input のパースと DB 引き当てを含む再利用可能なロジックで、
  contracts/services.py もしくは core 側（documents に対称物が無いので services で可）に
  置く方が役割分担の慣習に沿う。保存時の検証ロジック filter_valid_related_ids /
  sync_related_contracts は既に services.py に分離されており、再描画側だけ views.py に
  残っている非対称。

補足:
  純粋に「表示のための整形」であり副作用は無い（コメントでもその旨明記）。影響は小さく、
  緊急性は無い。同種の整形ヘルパー（_strip_ext, _edit_delete_context, _pending_preview_context）
  は documents 側にも views.py 直書きで存在するため、統一方針を決めてまとめて移すのが望ましい。

見送り／理由: 優先度「低」。副作用の無い表示用整形であり動作・保守性への実害が小さい。
  documents/contracts 双方の同種ヘルパー（_strip_ext 等）をまとめて services へ移す横断作業と
  して扱うべきで、_resolve_related_rows だけ単独で移すと逆に非対称が増える。別タスクで一括対応。

No.3  【低】 フォームの非自明メソッドに docstring が無い
--------------------------------------------------------------------------------
対象:
  - documents/forms.py  UploadStep2Form.__init__（127-199行）, clean は無いが SearchForm.__init__（310-348）, SearchForm.clean（350-354）
  - contracts/forms.py  UploadStep2Form.__init__（137-191）, UploadStep2Form.clean（193-204）,
    SearchForm.__init__（300-357）, SearchForm.clean（358-362）
  - contracts/api.py  CommaNumberInput.value_from_datadict / format_value（クラス docstring はあるがメソッド単位は無し）

根拠:
  CLAUDE.md「クラス・非自明なメソッドにはdocstringを付ける」。
  各 __init__ はフィールドのファイル数ぶん複製、部署 disabled 化、queryset 差し替え、
  検索部署デフォルト補完など 40〜60 行の非自明な処理を持つが、説明は行内コメントのみで
  メソッドの目的・責務を要約する docstring が無い。file_data / first_error_file_index には
  docstring が付いており、同一ファイル内で粒度が不統一。

見送り／理由: 優先度「低」。各 __init__/clean には既に「なぜ」を説明する行内コメントが
  十分に付いており、機能・可読性への実害は無い。docstring 粒度の統一は documents/contracts
  両 forms.py をまとめて見直す軽微整形タスクとして別途対応。

No.4  【低】 例外の握りつぶしに「なぜ」コメントが無い箇所
--------------------------------------------------------------------------------
対象:
  - contracts/api.py:46-51  CommaNumberInput.format_value
        except InvalidOperation:
            return value           # ← 理由コメント無し
  - contracts/services.py:204-207  calculate_expiry_date
        except ValueError:
            return save_date.replace(month=2, day=28, ...)   # ← 理由コメント無し

根拠:
  CLAUDE.md「失敗を握りつぶして良いが、その場合は必ずコメントで理由を明記する」。
  - format_value は「不正な数値文字列はそのまま素で表示に回す」という意図だが明記が無い。
  - calculate_expiry_date の ValueError は 2/29 起点の閏年ずれ対策。対になる
    documents/services.py:201-206 _add_years には「2/29起点の場合の閏年ずれ対策」という
    コメントがあるが、contracts 側の同型コードには無く不統一。

補足:
  どちらも意図はコードから比較的読み取れるため実害は小さいが、規約が明示的に要求している
  項目であり、documents 側との対称性の観点でも 1 行追記が望ましい。

見送り／理由: 優先度「低」。挙動に影響せず、意図もコードから読み取れる。コメント 1 行の
  追記のみで独立してテストが伴わないため、次に当該ファイルを触る際に併せて対応する。

No.5  【低】 models.py の logger が未使用
--------------------------------------------------------------------------------
対象:
  - documents/models.py:9   logger = logging.getLogger(__name__)
  - contracts/models.py:12  logger = logging.getLogger(__name__)

根拠:
  CLAUDE.md「新しいモジュールでは logger = logging.getLogger(__name__) を用意する」に
  従った定義だが、両モジュールとも実際には一度も参照していない（save 等のロジックは
  core.models のミックスインにあり、models.py 本体に警告すべき分岐が無い）。
  規約準拠としては「用意する」を満たしているが、未使用ローカル/シンボルとして lint 上は
  ノイズになる。documents/services.py は同じ状況に対し
  「現状このモジュールに警告すべき分岐は無い」と明示コメントを付けて意図を示しているため、
  models.py 側にも同様の一言を添えるか、実際に使うまで定義を保留するかで統一するとよい。

見送り／理由: 優先度「低」。規約「新しいモジュールでは logger を用意する」は満たしており、
  lint ノイズという程度の指摘。挙動・テストに影響しないコメント追記のみのため見送り。

確認したが問題なしと判断した項目（誤検知防止の記録）
================================================================================
- documents/contracts の UploadStep2View.post で commit 後に呼ぶ
  try_immediate_text_layer_extraction は core 側で広域 except＋logger.exception＋
  「アップロード自体を失敗させない」設計判断コメントを持つため、ビュー側の未捕捉は問題なし。
- transaction.atomic() ロールバック時の孤児ファイル削除（created ループの file.delete）は
  両ビューで実装済み。
- multi-line の {# ... #} コメントは各行が {# で始まり #} で終わる自己完結形で、
  CLAUDE.md が警告する「.が改行にマッチせず生表示される」パターンには該当しない。
- documents.services.document_searchable_department_ids と
  permissions.services.contract_searchable_department_ids の配置非対称は、
  依存データ（権限管理アプリ固有データの有無）と循環 import 回避の理由が docstring に
  明記されており意図的。
- 二重送信対策は core.double_submit のトークン方式で両アプリ横断実装済み（規約の
  「共通処理は core 集約」に合致）。
