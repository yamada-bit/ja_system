【C-1】優先度: 中   保存満了日(expiry_date)の編集時再計算が「単体編集 / 一括編集の未変更ページ /
                     契約書」で三者三様
────────────────────────────────────────────────────────────────
該当:
  - documents/services.py:130  apply_document_edit
      doc.expiry_date = calculate_expiry_date(timezone.localdate(), cleaned_data["retention_period"])
  - documents/services.py:141-156  document_edit_is_dirty（コメント「保存期間が変わらない限り
    実質不変」）
  - contracts/services.py:59-95  apply_contract_edit … expiry_date を一切更新しない
  - documents/views.py:472-546  BulkEditView._commit（dirtyページのみ apply_document_edit を通る）

内容:
  文書の単体編集(DocumentEditView)は、どの項目を変えても毎回
  expiry_date = 今日 + 保存期間 で上書きする。calculate_expiry_date は「今日」基準なので、
  登録から時間が経った文書をタイトル修正しただけでも保存満了日が経過日数ぶん先送りされる。
  一方、一括編集の確定は dirty 判定を通ったページだけ apply_document_edit を呼ぶため、
  「無関係な項目に触れた文書」は満了日が更新され、「一切触れていない文書」は据え置きになる。
  契約書側(apply_contract_edit)は編集時に expiry_date を触らない。
  → 同じ保存期間の2文書が、無関係な項目に触れたか否かだけで保存満了日が変わる。

  加えて document_edit_is_dirty のコメント「保存期間が変わらない限り実質不変」は誤り
  （今日基準の派生値なので毎日変わる）。CLAUDE.md「コメントは『なぜ』を詳しく書く」に対して
  誤った根拠が書かれている状態。

想定シナリオ:
  - 2024-01 登録・保存期間5年（満了 2029-01）の文書のタイトル誤字を 2026-08 に修正
    → 満了日が 2031-08 へ。メイン画面お知らせ「有効期限切れ」抽出・自動物理削除バッチの
      対象判定がズレる。
  - doc_retention_edit（権限管理!B172-175「保存満了日変更」）が OFF の職員でも、
    保存期間欄は disabled で触れないが、他項目を編集するだけで満了日を先送りできてしまう。

対応方針（要ユーザー確認）:
  「編集＝再保存として満了日を今日基準で引き直す」が仕様なら、contracts と単体/一括で挙動を
  統一し、document_edit_is_dirty の比較対象にも expiry_date（または retention_period ＋
  基準日）を含める。仕様でないなら apply_document_edit の当該行を削除し、保存期間変更時のみ
  引き直す。

【C-2】優先度: 中   契約書編集で関連書類(RelatedFile)保存が途中失敗すると物理ファイルが孤児化
────────────────────────────────────────────────────────────────
該当:
  - contracts/services.py:87-95  apply_contract_edit の with transaction.atomic():
        RelatedFile.objects.create(contract=contract, file=related, ...)
  - 呼び出し元: contracts/views.py:347 ContractEditView.post / contracts/views.py:618
    BulkEditView._commit

内容:
  RelatedFile.objects.create() は生成時点でストレージへファイルを書き込む。複数追加の
  2件目以降や本体 save() で DBError 等が発生すると、inner transaction.atomic() は
  RelatedFile 行・Contract 行をロールバックするが、既に書き込まれた物理ファイルは残る。
  これは documents/views.py:164-182・contracts/views.py:226-243 の「登録」経路が
  明示的にコメント付きで対処している孤児ファイル問題と全く同型だが、編集経路（単体・一括とも）
  では未対処。tmp_uploads と違い MEDIA_ROOT 配下の孤児は定期クリーンアップの仕組みが無い
  （core/upload_services.py clear_pending_files docstring 参照）。

想定シナリオ:
  ContractEditView で関連書類を2件追加 → 2件目の create でストレージ書き込みエラー
  → 例外は views 側で捕捉されリダイレクトされるが、1件目のファイル実体は MEDIA_ROOT に残存。
  失敗のたびに蓄積。

対応方針:
  apply_contract_edit 内で新規作成した RelatedFile.file を except 節で file.delete(save=False)、
  または作成済みファイル参照を呼び出し側へ返し「登録」経路と同じ後始末に寄せる。

【C-9】優先度: 低   複数ファイル一括登録で「DB挿入に失敗したファイル」だけ孤児化
────────────────────────────────────────────────────────────────
該当:
  - documents/views.py:147-163（temp_file→file.save→document.save→created.append の順）
  - contracts/views.py:203-225（同様）

内容:
  document.file.save(name, temp_file, save=False) はストレージへ即書き込むが、
  created.append(document) は document.save()（DB INSERT）成功後。N件目の save() が DBError の
  場合、その file 実体は created に無いため except 節の後始末ループ（created の file.delete）の
  対象から漏れ、孤児化する。C-2 と同じ「DBロールバックはファイル実体を戻さない」クラス。

対応方針:
  file.save 実行後・document.save 前に後始末候補リストへ積む。
