[高] H-1. 「保存満了日は保存期間変更時のみ引き直す」ルール（C-1）が4経路とも未検証
--------------------------------------------------------------------------------
対象:
  - documents/services.py apply_document_edit()
      retention_changed 判定 → True のときだけ
      doc.expiry_date = calculate_expiry_date(timezone.localdate(), ...)
  - documents/services.py document_edit_is_dirty()
      （expiry_date を比較対象に含めない設計の妥当性）
  - contracts/services.py apply_contract_edit()
      「expiry_date は編集時に一切触らない」
  - contracts/services.py contract_edit_is_dirty()

内容:
  2026-08-28 にユーザーが確定し memory (expiry_date_edit_recalc_spec) にも記録された業務
  ルール「編集時に expiry_date を今日基準で引き直すのは保存期間を変更したときだけ
  （文書単体／一括／契約書の3経路で統一）」に対する回帰テストが1件も無い。

  - documents.tests.EditScreenRetentionPermissionTests は retention_period フィールドの
    変更可否（doc_retention_edit フラグ）だけを assert し、変更後の expiry_date の値は
    一切検証していない（setUp は expiry_date=2099-01-01 のダミー値で、_post_edit 後に
    その値が引き直されたか／据え置かれたかを見ていない）。
  - documents.tests.CalculateExpiryDateTests / contracts.tests.CalculateExpiryDateTests は
    calculate_expiry_date() 単体（年加算・月加算・永年・閏日）のみで、編集経路で
    「呼ばれる／呼ばれない」の分岐は対象外。
  - contracts 側は「apply_contract_edit は expiry_date を触らない」ことを確認するテストが
    皆無（ContractEditViewFileHandlingTests は関連書類まわりのみ）。

  このルールは (a) 直近まで「毎回 今日+保存期間 で上書き」という真逆の挙動だった、
  (b) 3経路で挙動を揃えることが要件、という経緯があり、共通ヘルパーの将来の改修で
  片方の経路だけ挙動が戻っても現状は誰も気付けない。ユーザー確定済みルールとしては
  回帰保護の優先度が高い。

対応方針（参考、修正はまだしない）:
  1. documents: 保存期間を変えずにタイトルだけ編集 → expiry_date が変化しないこと。
     保存期間を 1年→3年 に変更（doc_retention_edit=True）→ expiry_date が
     timezone.localdate()+3年 に引き直されること。
  2. documents: 一括編集で保存期間を変えずに他項目だけ変更したページの expiry_date が
     据え置かれること（BulkEditViewTests に1件追加）。
  3. contracts: ContractEditView / BulkEditView で編集しても expiry_date が
     登録時の値のまま不変であること。
  4. document_edit_is_dirty / contract_edit_is_dirty の直接テスト（指摘 M-2 と統合可）。

[中] M-2. document_edit_is_dirty / contract_edit_is_dirty の直接ユニットテストが無い
--------------------------------------------------------------------------------
対象:
  - documents/services.py document_edit_is_dirty()
  - contracts/services.py contract_edit_is_dirty()（related_changed 引数含む）

内容:
  一括編集の「更新なし」判定（保存も監査ログもスキップ）を左右する中核ロジックだが、
  BulkEditViewTests の HTTP 経由（「タイトルを変えたページだけ更新」）でしか間接検証
  されていない。以下の境界が個別に固定されていない:
    - privacy_flag: bool(doc.privacy_flag) != bool(cleaned_data["privacy_flag"])
      （"True"/"False" 文字列 ↔ bool の比較差異）
    - memo: (doc.memo or "") != (cleaned_data["memo"] or "")（None ↔ "" の正規化）
    - department: 非管理者は cleaned_data["department"] を employee.department に
      読み替えてから比較する（can_select_department 分岐）
    - contract_edit_is_dirty の related_changed=True 単独で dirty になること
    - year / 各日付 / contract_amount(Decimal) の同値判定

  特に「非管理者が自部署以外を POST してきても department 差分としては検出しない」
  （view 側で自部署固定するため）という非自明な仕様は、この関数単体でしか確認できない。

対応方針（参考）:
  services 関数を直接呼ぶ ...ServiceTests クラスを両アプリに新設し、上記各境界について
  is_dirty が期待どおり True/False を返すことを assert する。H-1 の
  「expiry_date を比較対象に含めない」検証もここに含められる。
