優先度「高」「中」に該当する、確度80%以上で悪用可能な新規脆弱性は

本リポジトリは過去に複数回のセキュリティ／コードレビューを経ており、
以下のような防御パターンが全体で一貫して適用されていることを確認した。

  - 検索・一覧・API はすべて Django ORM（パラメータ化クエリ）。生SQL・
    文字列連結クエリ・.raw()/.extra() は無し。HealthCheckView の
    `SELECT 1` のみ生SQLだが定数（core/views.py:294）。
  - ファイル保存パスは core/storage_paths.py が UUID プレフィックス＋
    Django 5.2 の FileField/Storage 側パストラバーサル検証に委譲。
  - ファイル配信（core/record_views.py BaseFileServeView）は
    scoped_lookup による部署スコープ検証 → can_download 権限検証 →
    resolve_as_attachment で PDF・画像以外はインライン配信させず添付化 →
    apply_file_response_security_headers で nosniff／実行禁止CSP を付与。
  - AJAX API（core/api.py, documents/api.py, contracts/api.py,
    organizations/api.py）は LoginRequiredMixin ＋ 部署スコープ
    （visible_department_ids / contract_searchable_department_ids）＋
    権限フラグ（RequiresContractEditMixin 等）＋ 越境アクセス時の
    audit ログ（log_denied_cross_department_access）を実装。
  - CSV 出力（audit/views.py, accounts/views.py, permissions/views.py）は
    すべて core.csv_services.sanitize_csv_row で数式インジェクション対策済み。
  - テンプレートの onclick／inline JS へのユーザー値埋め込みは Django の
    `|escapejs`、クライアント JS の innerHTML 組み立ては common.js の
    escapeHtml() でエスケープ済み（related 検索結果は DOM API で構築）。
  - 一括編集の確定時（core/bulk_edit_services.py）に部署スコープと
    is_deleted を再検証（コミット bbe79c7 で追加済み）。
  - CSV 取込（accounts/csv_import_services.py）は職員番号 NFKC 正規化＋
    数字検証、rank/position の choices 検証、管理者0人ガード
    （LastAdminError＋行ロック lock_active_admin_profiles）を実装。
  - 認証は Django カスタムユーザー＋Argon2、DEBUG 既定 False、
    DB 既定ロールは最小権限 ja_app。

本ブランチの差分の大半はドキュメント（CLAUDE.md・チェックリスト類）と
原本フィデリティ追随、および防御的なハードニング（middleware の例外種別を
DatabaseError に限定する等）であり、新規の攻撃面はほぼ増えていない。
新規追加の PDF.js プレビュー（static/js/pdf-preview.js）／関連書類検索
（contracts.api.RelatedSearchAPIView）も、URL はサーバー側 reverse() 生成、
検索範囲は既存の閲覧スコープに一致させており問題は認められない。

No.1  関連契約書タイトルの部署スコープ越え開示
--------------------------------------------------------------------
対象ファイル : contracts/api.py:106-117
              （DetailAPIView.get の "related_contracts" 生成）
              static/js/common.js:758-767（renderRelatedResourceLink）
カテゴリ     : data_exposure（情報開示）
確度         : 中（7/10）— 仕様上「関連書類を見せる」機能の設計意図と
              解釈する余地があり、影響も限定的
深刻度       : 低

説明 :
契約書詳細ポップアップ API（DetailAPIView）は、閲覧中の契約書に紐付いた
関連契約書について title / is_deleted / preview_url を返す。preview_url は
「ダウンロード権限あり かつ 未削除」でのみ埋められ、PDF 実体の配信
（contracts:preview → BaseFileServeView）は scoped_lookup で部署スコープを
サーバー側再検証するため保護されている。しかし title 文字列は、閲覧
ユーザーの部署スコープ（contract_searchable_department_ids）が当該関連
契約書の所属部署を含むかに関わらず、常に JSON 応答に含まれる。

想定される悪用シナリオ :
関連付けは RelatedSearchAPIView 側で作成者の閲覧範囲に制限されるため、
「作成者は部門間閲覧設定で契約書 B を見られたが、後から契約書 A だけを
閲覧できる別ユーザー（B の部署は範囲外）」が契約書 A の詳細ポップアップを
開くと、本来閲覧範囲外である契約書 B のタイトル（取引先名・案件名等の
機微を含みうる）を取得できる。API 直叩き（GET /contracts/api/detail/<A>/）
でも同じ。PDF 本体やその他メタデータは取得できず、開示範囲はタイトル1項目。

根拠 :
- contracts/api.py:110-114 は preview_url を can_dl / is_deleted のみで
  gating し、link.related_contract.department が閲覧スコープ内かを見ていない。
- 同ファイル 62-75 の本体契約書に対する越境チェック
  （contract_searchable_department_ids ＋ log_denied_cross_department_access）
  と対称になっていない。
- 本アプリでは部署スコープが download 権限より強い分離境界として
  扱われている（search_services.build_queryset の department_id__in 絞り込み、
  BaseFileServeView の scoped_lookup）。

修正の方向性（コードは変更していない）:
DetailAPIView で related_contract ごとに
contract_searchable_department_ids(request.user) を評価し、範囲外の
関連契約書は応答から除外する、またはタイトルを伏せ字にして
「（閲覧権限がありません）」等のラベルに置き換える。仕様担当と、
関連書類欄における部署スコープの扱い（download 権限不足時の素テキスト
表示と同列に扱うか、完全に隠すか）を確認した上で対応する。

対応 : 見送り
理由 : 優先度「低」。開示範囲は関連契約書のタイトル1項目のみで PDF 実体・
       その他メタデータは scoped_lookup で保護済み。かつ「関連書類を見せる」
       機能の設計意図と解釈する余地があり（確度 7/10・深刻度 低）、修正すると
       仕様上どちらが正か（伏せ字か完全除外か）を仕様担当と確定する必要がある。
       ユーザー指示によりコード修正は行わず、リリース前の仕様確認事項として
       記録するに留める。

追補監査  副作用エンドポイントのサーバーサイド権限チェック等（既存コード対象）
====================================================================
対象      : documents/ contracts/ permissions/ organizations/ masters/ の
            全 View・api.py（＋委譲先の core.record_views / core.bulk_edit_views /
            core.upload_views / core.scoping_services / core.api）
実施日    : 2026-09-10
観点      : (a) 削除／編集／ダウンロード／一括ダウンロード／権限変更など副作用の
              あるエンドポイントで、クライアント側のボタン非表示だけに頼らず
              View.post / API 側でサーバーサイド権限チェックが実装されているか
              （URL 直打ち・セッション改ざんでバイパスできないか）
            (b) パスワード等の機微情報のハッシュ化・マスク表示
            (c) ファイルアップロード・PDF テキスト抽出など外部境界での
              具体的な例外型の捕捉・logger.exception・利用者向けエラー応答

--------------------------------------------------------------------
総評（追補）
--------------------------------------------------------------------
観点 (a)：副作用のある全エンドポイントについて、クライアント側の表示制御と
独立したサーバーサイドの権限・スコープ検証が一貫して実装されていることを
1 エンドポイントずつ確認した。優先度「高」「中」の逸脱は検出されなかった。
確認した主な防御：

  - 文書／契約書の DownloadView・PreviewView・BulkDownloadView・DeleteView・
    EditDeleteView・DocumentEditView/ContractEditView・BulkEditView は
    いずれも core.record_views / core.bulk_edit_views の基底クラスに集約され、
      * scoped_lookup（*.services.scoped_get_object_or_404 → core.scoping_services）
        による部署スコープのサーバー側再検証（+ 越境時 audit ログ）
      * can_download / can_edit_contract / deletion_services.can_delete の
        サーバー側再判定（UI の delete_url=None・disabled と独立）
      * is_deleted=False での対象絞り込み（削除済みへの直打ち遮断）
    を必ず通す。DetailAPIView（api.py）も scoped_lookup 非経由のぶん
    department_id スコープ判定と log_denied_cross_department_access を直書きで
    持つ。
  - 契約書の保存・編集フロー（UploadStep1/2・ContractEditView・BulkEditStart/
    BulkEditView・ChunkUploadAPIView・PendingPreviewView・RelatedSearchAPIView）は
    RequiresContractEditMixin で contract_edit 権限を MRO 上 LoginRequiredMixin の
    後に強制。DeleteView も extra_permission_check で can_edit_contract を再判定。
  - 一括編集の確定経路（BaseBulkEditView._committable_pks / _commit）は、
    ウィザード開始後にスコープ外・論理削除済みになった pk を確定直前に再絞り込みし、
    削除マークも can_delete をサーバー側で再検証（toggle 時・commit 時の二重）。
  - 一括ダウンロード・一括編集開始の pks は生 POST 値として int 検証＋
    department_id__in ＋ is_deleted=False で絞り、範囲外は警告ログの上で静かに除外。
  - 設定系画面（部署管理・分類/カテゴリー管理・保存期間設定・権限管理一覧/CSV）は
    SettingsMenuAccessMixin が SETTINGS_MENU_VISIBLE_ROLES と同一のロール判定を
    dispatch で強制（ボタン非表示と別物）。分類/カテゴリーの編集・削除は
    masters.services.scoped_get_object_or_404 で非管理者を自部署のみに制限。
  - 権限管理編集（AuthorityEditView）は can_manage_target で対象職員単位の
    アクセス制御（所属長は自部署の一般職員のみ・自分不可）、AuthorityEditForm が
    role choices の絞り込みと contract_visible_departments フィールドの削除で
    昇格・管理者限定項目の改ざんをサーバー側で遮断、管理者0人ガードは
    lock_active_admin_profiles の行ロック付き。
  - チャンクアップロード API は upload_id を ^[0-9a-zA-Z-]{1,64}$ に制限、
    結合時の元ファイル名も Path(...).name で正規化（パストラバーサル対策）。
    能動的コンテンツ（HTML/SVG 等）は blocked_upload_message で受信時に拒否。

観点 (b)：対象 5 アプリにパスワード等の秘匿情報を扱う画面は無い（権限フラグ・
部署/分類名は秘匿情報に当たらない）。ログイン画面・職員マスタ側のマスク表示
（●●●●●●）は本追補の対象外だが既存レビューで確認済み。

観点 (c)：外部境界の例外処理は要件を満たしている。
  - core.upload_services（save_pending_files / open_pending_file /
    save_upload_chunk / combine_upload_chunks）は OSError を具体捕捉し
    logger.exception → PendingFileStorageError / ChunkUploadError にラップ、
    呼び出し側 View が messages.error で利用者向け応答。
  - UploadStep2View.post・ContractEditView.post・DocumentEditView.post・
    BaseBulkEditView._commit・RetentionDeleteView.post 等の DB 境界は
    django.db.Error（DBError）を具体捕捉し logger.exception ＋ messages.error。
  - core.text_extraction_services.try_immediate_text_layer_extraction のみ
    `except Exception` だが、「1 件の本文抽出失敗でアップロード自体を失敗に
    しない・次回バッチで再試行」という設計判断がコメントで明記され
    logger.exception も出力（CLAUDE.md「本質的でない処理の失敗で本処理を
    巻き込まない場合は理由明記の上で握りつぶし可」に合致）。bare `except:` は
    対象範囲に存在しない。

No.2  権限管理の選択肢 API がロール未ゲートで全部署・全契約書分類を返す
--------------------------------------------------------------------
対象ファイル : permissions/api.py:13-41
              （OptionListAPIView。URL: GET /permissions/api/options/?type=...）
カテゴリ     : broken_access_control / data_exposure（情報開示・スコープ迂回）
確度         : 高（9/10）— コード上明白、コメント自体が既知の見送りとして記載
深刻度       : 低

説明 :
権限管理編集画面（screen-authority-edit）の「部門間閲覧設定」「分類表示設定」
ポップアップが叩く選択肢 API。実装は LoginRequiredMixin のみで、背後の画面が
持つロール制限（authority_management = 管理者／所属長）をサーバー側で課して
いない。そのため一般（STAFF）ロールを含む任意のログインユーザーが

  GET /permissions/api/options/?type=dept
      → 全部署（本支所名｜部課名）の一覧
  GET /permissions/api/options/?type=group&doc_kbn=contract
      → 全部署横断の契約書向け分類名の一覧
  （?type=group&doc_kbn=document も同様）

を直接取得できる。type=dept は全 Department、type=group は
Group.objects.filter(doc_kbn=..., is_deleted=False) を部署スコープ・
visible_groups 一切なしで返す。

想定される悪用シナリオ :
通常の検索・保管画面の popup-select は core.api.BaseOptionListAPIView 経由で
visible_groups() と department_ids_for_group_scope() により「自部署ぶんの
分類のみ」に絞られる。一般ロール職員がこの permissions 側エンドポイントを
直接叩くと、その絞り込みを迂回して他部署を含む契約書分類マスタ・部署マスタの
全名称を列挙できる。開示されるのは名称のみで、文書・契約書の実体、件数、
個人情報、権限設定の中身は取得できず、PermissionProfile を変更する手段も無い。

根拠 :
- permissions/api.py:13 の class 宣言が `LoginRequiredMixin, View` のみ。
  同 24-30 のクラス docstring が「一般ロールでも ?type=dept 等を直接叩いて
  取得できる…実害は限定的と判断し見送った」と明記（コード監査 2026-08-25）。
- 対になる organizations/api.py:38-47 の OptionListAPIView は、同種の
  「全部署を返す管理者向けポップアップ API」でありながら dispatch() を
  オーバーライドして can_access_settings_menu_item(request.user,
  "dept_management") をサーバー側で強制しており、非対称。
- core/api.py:59-98 の BaseOptionListAPIView は visible_groups /
  department_ids_for_group_scope / scope_queryset_by_department で
  部署スコープを適用しており、こちらとも非対称。

修正の方向性（コードは変更していない）:
organizations/api.py:38-47 と同じパターンで dispatch() をオーバーライドし、
未認証は handle_no_permission()、認証済みは
can_access_settings_menu_item(request.user, "authority_management")
で 403 にする（SettingsMenuAccessMixin は BaseOptionListAPIView 系と MRO が
衝突するため直接ミックスインできない点も organizations 側と同じ）。あわせて
type=group / type=dept の結果を permissions.services の
visible_groups / contract_searchable_department_ids でスコープするかは、
「部門間閲覧設定は他者に閲覧を許可する側の設定で閲覧者自身のスコープとは
無関係」（同ファイル docstring）という位置づけを踏まえ仕様担当と確認する。

対応 : 見送り
理由 : 優先度「低」。開示されるのは部署名・契約書分類名の名称のみで、文書・
       契約書の実体、件数、個人情報、権限設定の中身は取得できず、
       PermissionProfile を変更する手段も無い。permissions/api.py の
       クラス docstring に既知の見送り（コード監査 2026-08-25）として
       明記済みの事項であり、本ブランチの新規事項ではない。ロールゲート
       追加自体は organizations/api.py と同じパターンで可能だが、あわせて
       検討すべき type=group / type=dept のスコープ方針が仕様担当の確認
       待ちのため、ユーザー指示により今回はコード修正を行わず見送る。
