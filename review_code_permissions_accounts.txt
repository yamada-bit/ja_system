No.1  優先度: 中
対象: permissions/views.py:153-161  AuthorityEditView.dispatch
現象:
  未認証（AnonymousUser）で /permissions/<存在するpk>/edit/ を GET すると、
  ログイン画面へのリダイレクト（302）ではなく HTTP 500 になる。
根拠:
  - AuthorityEditView は dispatch() を独自オーバーライドしており、その中で
    まず get_object_or_404() → can_manage_target(request.user, self.employee)
    → logger.warning(... request.user.employee_no ...) を実行し、その後で
    super().dispatch()（= LoginRequiredMixin.dispatch の認証チェック）を呼ぶ。
    つまり認証チェックより前に request.user を権限判定に使ってしまう。
  - can_manage_target() は get_role() → get_profile() で
    employee.permission_profile にアクセスするが、AnonymousUser には
    permission_profile が無く、get_profile() の except は
    PermissionProfile.DoesNotExist しか捕捉しないため AttributeError が素通りする。
    （実機確認済み: get_role(AnonymousUser()) →
     AttributeError("'AnonymousUser' object has no attribute 'permission_profile'")）
  - request.user.employee_no も AnonymousUser では存在しない。
  - permissions/mixins.py SettingsMenuAccessMixin の docstring が
    「LoginRequiredMixin より先に実行されると未ログイン時に get_role() が
    AnonymousUser を渡されて意図しない挙動になる」とまさにこの順序問題を警告している。
    AuthorityListView / AuthorityCsvExportView / accounts 側の各ビューは
    LoginRequiredMixin を先に効かせているため影響なし。AuthorityEditView だけが
    自前 dispatch でこの前提を崩している。
補足（altitude）:
  対処は (a) AuthorityEditView.dispatch の先頭で未認証なら super().dispatch() に
  委譲してから独自チェックを行う、または (b) get_profile()/get_role() を
  未認証ユーザーに対して安全にする（AttributeError も None 扱い）、のいずれか。
  (b) の方が横展開に強い（同種のビューが将来増えても防げる）。
対応済み（2026-09-10）:
  (a)(b) 両方を実施。AuthorityEditView.dispatch の先頭で request.user.is_authenticated が
  False なら独自チェックを一切行わず super().dispatch() へ委譲（LoginRequiredMixin が
  ログイン画面へ 302）。あわせて permissions/services.py get_profile() が AttributeError も
  捕捉して None を返すよう変更（未認証時に権限が緩む方向には働かない＝None は最も制限の
  強い扱い）。permissions/tests.py に未認証 GET が 302 になる回帰テストを追加。

No.2  優先度: 中
対象: permissions/services.py:33-65  admin_count / would_orphan_admins
現象:
  「システム管理者が0人にならない」ガードが check-then-act であり、
  並行操作で最後の2人の管理者を同時に降格すると両方がガードを通過し0人化しうる。
根拠:
  - admin_count() は PermissionProfile.objects.filter(...).count() の素の集計で、
    select_for_update 等の行ロックが無い。
  - would_orphan_admins() を使う経路が複数ある:
    権限管理編集(AuthorityEditForm.clean_role)、CSV取込の所属長フラグ降格
    (_apply_manager_flag)、本支所〜役職変更・退職に伴うリセット
    (reset_permission_profile_if_needed)。
    管理者Aの降格リクエストと管理者Bの降格リクエスト（別セッション／CSV取込中の
    別行／CSV取込と手動編集の同時実行）が並走すると、双方が
    admin_count(exclude=自分) == 1 を見て両方 commit し、結果0人になる。
  - 「管理者1人以上」を保証する DB 制約（部分unique等）が無いため最終防衛も無い。
影響度: 実運用で同時降格が起きる頻度は高くないが、ガードの存在意義そのものに
  穴がある。少なくとも各更新経路で対象 PermissionProfile 行を
  select_for_update() で確定してから admin_count するか、行数の下限を保証する
  仕組みの検討が望ましい。
対応済み（2026-09-10）:
  permissions/services.py に lock_active_admin_profiles() を追加（在職中 role=ADMIN の
  PermissionProfile 行を SELECT ... FOR UPDATE OF self でロック）。降格を行う3経路すべてで、
  transaction.atomic() 内・would_orphan_admins()/admin_count() の判定より前にこれを呼ぶ：
   - AuthorityEditForm.clean_role 経路：AuthorityEditView.post で is_valid()＋save() を1つの
     transaction.atomic() で囲み、先頭で lock_active_admin_profiles()。
   - _apply_manager_flag（CSV所属長フラグ降格）：_import_row の atomic 内で would_orphan_admins
     の直前にロック。
   - reset_permission_profile_if_needed（本支所〜役職変更・退職に伴うリセット）：関数内の
     判定〜保存を transaction.atomic() で明示的に囲み、先頭でロック（呼び出し側も従来どおり
     atomic だが単体でも競合に強くした）。
  2つ目以降のトランザクションは1つ目の commit まで待たされ、待機解除後の admin_count が減った
  人数を見て正しく中止する。permissions/tests.py に FOR UPDATE 発行の回帰テストを追加。

対象: accounts/csv_import_services.py:236-264  _apply_manager_flag
現象:
  PermissionProfile がまだ無い「既存職員」に所属長フラグ "1" が付いた行を取り込むと、
  権限は MANAGER になるのに AuditLog（操作履歴ログ）に一切記録されない。

  - profile, _ = PermissionProfile.objects.get_or_create(
        employee=employee, defaults={"role": PermissionRole.MANAGER})

    で早期リターンし、その先の audit_services.log(...) を通らない。
  - 新規職員ブランチ(_import_employee 内)は明示的に STAFF の profile を作るため
    影響しないが、「既存職員だが権限管理で未設定」は get_profile() が None を返す
    正常状態として存在しうる（permissions/services.py get_profile docstring）。
  - 本改修の意図（コメント: 「CSV取込経由の所属長昇格が /audit/ 画面から
    追跡できなかった」ため audit ログを追加）と矛盾する抜け。
  - 旧実装も同じ挙動のため厳密には本PRの回帰ではないが、周辺を触っている今が
    直しどき。get_or_create の created フラグを見て、新規作成時も audit ログを
    出すのが筋。
見送り（2026-09-10）／理由:
  優先度「低」。旧実装からの既存挙動で本PRの回帰ではない。発生条件は「既存職員かつ権限管理で
  PermissionProfile 未設定（get_profile()=None の正常状態）かつ CSV 所属長フラグ"1"」に限られ、
  実データではほぼ出現しない周辺ケース。No.2 対応で _apply_manager_flag は触っているが、
  get_or_create の created 分岐で audit ログを出す修正は今回の対応方針（高・中のみ修正）から外れる
  ため見送る。将来 audit ログの網羅性を見直す際に併せて対応する。
