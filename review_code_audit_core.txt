      documents/contracts の BulkEditView に dept_ids_resolver を設定
      （dept_ids_resolver 未設定サブクラス〈保管画面２〉は is_deleted のみ再確認）。
      検証: python manage.py test audit core（167）OK、全体（918）OK。

      一括編集の「更新」確定処理が、ページ巡回時に効いている部署スコープ・
      is_deleted フィルタを再適用していない。

      ・_current_object()（各ページ表示）は scoped_lookup（= *.services.
        scoped_get_object_or_404、部署スコープ強制）と base_queryset()
        （is_deleted=False）を通す。
      ・一方 _commit() は commit_queryset(pks) でロードする。既定実装は
        `self.model.objects.filter(pk__in=pks)` のみで、documents/contracts の
        サブクラスも override していない（documents/views.py BulkEditView、
        contracts/views.py BulkEditView 参照。contracts 側は prefetch を足すだけ）。
      ・_commit は state["pks"] 全件をループして更新・論理削除する。「現在表示中の
        ページ」だけは post() 冒頭の _current_object() でスコープ検証されるが、
        表示中でない他ページの pk は commit 時に一切スコープ検証されない。

      想定される失敗シナリオ:
        (a) ウィザード開始後に管理者が当該職員の閲覧部署範囲（DepartmentViewScope）を
            縮小 → 既にステージ済みの他ページの編集/削除マークが、その職員が
            もう閲覧できない他部署レコードに対してそのまま確定される。
        (b) 別タブ／他ユーザーが対象の1件を論理削除した後に「更新」 →
            commit_queryset に is_deleted=False が無いため、論理削除済みレコードに
            対して編集が走り「更新」監査ログまで残る（ゴミ箱内のまま値だけ書き換わる）。

      根拠: resolve_ordered_pks は「開始時点」のスコープ・is_deleted しか保証しない
      （core/bulk_edit_services.py docstring も「開始時」と明記）。HTML_REIMPL_
      CHECKLIST_ARCHIVE.md は「部署スコープは scoped_get_object_or_404＋
      resolve_ordered_pks で強制済み」としているが、確定経路は両者を通らない。
      CLAUDE.md「ボタンの表示/非表示と…サーバー側権限チェックは別物」「URL直打ちを
      想定してサーバー側も確認する」の趣旨に一致。

      推奨: commit_queryset の既定を base_queryset() ベース（is_deleted=False ＋
      scoped_lookup と同じ部署条件）にする、または _commit のループ内で
      scoped_lookup 相当の再検証を行う。core 側の基底修正で両アプリに効く。

      後方互換: BaseBulkEditView は documents/contracts の BulkEditView からのみ
      継承。commit_queryset のシグネチャは維持できるため影響は無い。


No.2  [低]  core/bulk_edit_views.py  BaseBulkEditView._commit
      【見送り／理由: 優先度「低」。指示により低優先度は修正せず記録のみ。】
      audit_services.log() を transaction.atomic() ブロック内のループで呼んでおり、
      audit.services.log_raw() は `except Exception` で握りつぶす。

      atomic ブロック内で DB 例外を握りつぶすと、以降その atomic 内の DB 操作は
      Django が TransactionManagementError を送出する（既知のアンチパターン）。
      TransactionManagementError は django.db.Error のサブクラスのため
      `except DBError` に捕捉され、結果的にバッチ全体がロールバックし
      「更新に失敗しました」の一般メッセージになる。真因（AuditLog INSERT 失敗）は
      logger.exception のログにしか残らない。

      失敗シナリオ: 何らかの理由で AuditLog の INSERT が DataError 等になった場合、
      その1件だけでなくコミット対象全件が巻き戻り、原因が画面・監査ログから追えない。

      発生確率は低い（action は短い固定文字列、event_message は TextField）。
      根拠: audit/services.py:154-164、core/bulk_edit_views.py:561-599。
      CLAUDE.md の「握りつぶす場合は理由をコメントで明記」自体は満たしているが、
      atomic 内での使用は log() の docstring が想定していない使い方。

      推奨: 監査ログ記録を transaction.atomic() の外（コミット成功後）に出す。
      BaseDeleteView / BaseFileServeView は obj.save() 後・atomic 外で log() して
      いるので、それに揃える。


No.3  [低]  core/bulk_edit_services.py  resolve_ordered_pks
      【見送り／理由: 優先度「低」。指示により低優先度は修正せず記録のみ。】
      戻り値 `[pk for pk in valid_pks if pk in existing_pks]` は valid_pks が
      リストのため、POST の pks に重複値が含まれると重複したまま返る。

      失敗シナリオ: 改ざん/二重付与された pks=[5,5,5] → ウィザードが同一レコードを
      3ページ巡回。_commit の削除分岐で同一 pk に対し obj.save() と
      audit_services.log("…削除しました") が3回走り、操作履歴ログに重複行が出る
      （更新分岐は2回目以降 dirty 判定で「更新なし」になるため実害は削除側）。

      発生には POST 改ざんが必要（int 変換・存在確認は通過してしまう）。優先度低。
      推奨: `dict.fromkeys(valid_pks)` 等で順序を保ったまま重複除去する。

No.4  [低]  audit/views.py  AuditLogCsvExportView.get
      【見送り／理由: 優先度「低」。指示により低優先度は修正せず記録のみ。】
      `for log in qs:` を .iterator() なしで回し、HttpResponse で CSV 全体を
      メモリ上に構築している。操作履歴ログはシステム内で唯一「無制限に増え続ける」
      テーブル（audit/models.py コメントにも明記）。

      本ブランチで filter_audit_log_queryset に retention_cutoff_date() の下限が
      入り最大3ヵ月に頭打ちにはなったが、稼働の多い3ヵ月分（数万〜十数万行規模）を
      一括で Python モデル化＋メモリ上 CSV 化するとレスポンス遅延・ワーカーメモリ
      圧迫の原因になり得る。

      accounts / permissions の CSV 出力も同じ書き方だが、そちらは行数が職員数・
      プロファイル数で有界。audit だけが実質無界のインスタンス。

      根拠: audit/views.py:46-82。action 文字列変更でこの関数は本ブランチの
      変更対象に含まれる。
      推奨: StreamingHttpResponse ＋ qs.iterator() へ変更（audit のみでよい）。


No.5  [低]  audit/services.py  filter_audit_log_queryset / retention_cutoff_date
      【見送り／理由: 優先度「低」。指示により低優先度は修正せず記録のみ。】
      下限フィルタが `timestamp__date__gte=<date>` で、timestamp を ::date に
      キャストするため AuditLog の btree インデックス（Index(fields=["-timestamp"])）を
      範囲述語に使えない。一覧はページャの LIMIT ＋ -timestamp 並びで実害小だが、
      CSV 出力（全件走査）では毎回テーブル全体を走査してフィルタする。

      日単位の下限なので、`timezone.make_aware(datetime.combine(cutoff, time.min))` を
      作って `timestamp__gte=<aware datetime>` にすれば意味は同値でインデックスが効く。
      purge_expired_audit_logs 側（`timestamp__date__lt`）も同様に置換可能。
      根拠: audit/services.py:29,41、core/management/commands/purge_expired_audit_logs.py:29。
      優先度低（No.4 とセットで対応すると効く）。


No.6  [低]  core/bulk_edit_views.py  _render_complete / _context
      【見送り／理由: 優先度「低」（かつ「任意」）。指示により低優先度は修正せず記録のみ。】
      _render_complete は self.model.objects.filter(pk__in=pks) を select_related /
      prefetch_related なしでロードし、rows で obj.title 等を参照する。件数は利用者の
      選択数に有界のため実害は小さいが、contracts の完了画面は complete_context_extra
      で別途 _related_rows_for_contract(self.object) を引き直す構成。完了画面も
      base_queryset()/commit_queryset() の prefetch を再利用できると素直
      （現状 commit で読んだインスタンスを捨てて完了画面で読み直している）。
      根拠: core/bulk_edit_views.py:604-638。優先度低・任意。

  ── 規約適合方向の修正。既存 AuditLog 行に旧表記が残るがイベントメッセージ部分一致
