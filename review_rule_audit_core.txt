■ 総評
--------------------------------------------------------------------------------
両アプリとも規約遵守度は総じて高い。特に以下は良好:
  - ビューは全て CBV（audit/views.py、core/views.py、core/*_views.py の基底クラス群）。
  - モデルの verbose_name / help_text / docstring / エラーメッセージは日本語で統一。
  - コメントの「なぜ」が非常に手厚い（設計判断・既知の制約・レビュー経緯まで追跡可能）。
  - 監査イベントは audit アプリに一元化。「成功操作＋他部署 URL 直打ち」は AuditLog、
    「権限不足の拒否・pk 改ざん検出」は logger.warning 止まり、という規約の区分を厳密に踏襲。
  - 一覧のページネーションは全て Django Paginator。静的ページャーの残存なし。
  - 例外処理は bare except なし。広域 catch には理由コメントあり。
  - 重複ロジックの core 集約（record_views / scoping_services / deletion_services /
    zip_services / notice_services 等）が徹底されている。
  - ユニットテストが厚い（core/tests.py 2088 行、audit/tests.py も網羅的）。

以下は逸脱・不整合の指摘。高:0 / 中:2 / 低:9。

No.1  [中]  二重送信トークン処理の共通ヘルパー未使用
--------------------------------------------------------------------------------
対象ファイル:
  core/views.py
    - OtherSettingsView.post        (112-115行)
    - OtherMainEditView.post        (207-210行)
    - OtherLogoutEditView.post      (254-257行)

根拠（規約）:
  「共通処理は core 相当の共通基底クラス・サービス関数に集約し、アプリ間で重複する
   ロジックを増やさない。」

内容:
  上記3ビューはいずれも
      submitted_token = request.POST.get("token", "")
      if not consume_token(request.session, self.form_id, submitted_token):
          messages.error(request, "二重に送信された可能性があるため…")
          return redirect(<自分自身>)
  という4行パターンを手書きしている。core/double_submit.py の
  reject_if_resubmitted() は「同一の4行パターンが11箇所重複していたため集約」と
  docstring に明記されており、core/master_views.py（BaseScopedMasterRegistView/
  EditView/DeleteView）では実際に使用されている。3つの redirect 先はいずれも
  クエリ文字列なしの単純な redirect(name) / redirect(name, pk=pk) であり、
  reject_if_resubmitted の引数でそのまま表現できるため、集約漏れと判断する。

対応済み（2026-09-10）:
  上記3ビューの post 冒頭の4行手書きパターンを core/double_submit.py の
  reject_if_resubmitted() 呼び出しに置換。redirect 先はそれぞれ
  "core:other_settings" / ("core:other_main_edit", pk=pk) / "core:other_logout_edit"。
  未使用になった consume_token の import も除去。python manage.py test audit core
  （167件 OK）／全体（918件 OK）で確認。

No.2  [中]  DB 境界での広域 except Exception（具体的な例外型で捕捉すべき）
--------------------------------------------------------------------------------
対象ファイル:
  core/middleware.py  SessionIdleTimeoutMiddleware._get_timeout_minutes  (44行)

根拠（規約）:
  「ファイル I/O・外部境界（ストレージ、DB の制約違反等）は try/except で
   具体的な例外型を捕捉し、logger.exception(...) で原因を記録した上で…」

内容:
  SystemSetting.objects.first() の失敗を `except Exception` で捕捉している。
  想定しているのは「マイグレーション未適用・DB 未接続」であり、これは
  django.db.DatabaseError（OperationalError / ProgrammingError）で表現できる。
  Exception 全捕捉だと、SystemSetting モデルの属性名変更ミス等の実装バグまで
  黙って既定値フォールバックに倒れ、不具合の発見が遅れる。理由コメントはあるが
  規約が要求する「具体的な例外型」には合致していない。
  （比較: core/views.py の各 post は IntegrityError/DatabaseError を明示捕捉、
   core/middleware.py だけ粒度が粗い。）

対応済み（2026-09-10）:
  `except Exception` を `except DatabaseError`（django.db、OperationalError /
  ProgrammingError の基底）に限定。マイグレーション未適用・DB 未接続はこれで捕捉しつつ、
  属性名変更ミス等の実装バグは伝播させるようコメントも更新。python manage.py test
  audit core（167件 OK）／全体（918件 OK）で確認。

No.3  [低]  定義のみで一度も使われていない logger（デッドコード）
--------------------------------------------------------------------------------
対象ファイル / 行:
  core/csv_services.py:3
  core/forms.py:13
  core/templatetags/search_extras.py:7
  audit/models.py:8
  audit/forms.py:7

根拠（規約）:
  「新しいモジュールでは logger = logging.getLogger(__name__) を用意し、
   権限拒否・想定外の分岐・セキュリティ上意味のある事象は logger.warning で記録する。」

内容:
  上記5ファイルは logger を定義しているが logger.warning/info/exception 等の
  呼び出しが 0 件。規約の「用意する」には形式的に沿っているが、実質は未使用の
  行。ログすべき事象がないなら定義自体を削るか、あるべきログ（例: audit/forms.py
  の clean() での日付逆転はユーザーに ValidationError で返すため不要と割り切る等）
  の方針を明確化する。

見送り／理由: 優先度「低」のため修正しない。規約の「用意する」には形式的に沿っており、
  現状ログすべき事象が無い（例: audit/forms.py の日付逆転は ValidationError で
  ユーザーに返すため logger 不要）。将来ログを足す際の受け皿として定義を残す方が
  追加コストが小さく、デッドコード除去の実益に乏しい。No.4 と併せた「logger 整備
  方針の明文化」は CLAUDE.md 側の課題として残す。

見送り／理由: 優先度「低」のため修正しない。「監査ログの記録失敗で本処理を巻き込ま
